## Product and users

Evolve DocLens into a **version-aware, permission-aware engineering support and incident knowledge assistant**. Engineers investigating failures should be able to combine product references, release notes, repository runbooks, and past tickets, inspect the evidence, distinguish applicable releases, and see conflicts or missing evidence. The assistant recommends documented procedures; autonomous production changes are outside this plan.

The user clarified two simultaneous goals: a useful public application for real engineering questions, and an inspectable demonstration of strong RAG/backend engineering. Synthetic material is welcome when deliberate and labeled, but is optional rather than the main knowledge base's foundation. Both public questions and guided scenarios must execute the actual retrieval/generation/validation pipeline; example buttons must not return canned answers. Provider unavailability is shown honestly, without paid fallback or a replay disguised as a new answer.

**Recommended initial audience:** Python developers maintaining cross-platform file-processing and backup tools on Python 3.12/3.13. **Focused problem:** choosing documented file/path operations and understanding version, platform, cleanup and metadata limits when those tools behave unexpectedly. This is a recommendation for the initial public collection, not a claim that the user selected a new domain. It reuses ten already inspected pages, supports the five practical questions below, and makes source qualifications important to real decisions. It is deliberately narrower than a general programming chatbot. A cloud-native/OpenTelemetry/Kubernetes collection remains an unselected alternative; do not silently switch domains or present a domain comparison as validated demand research.

Maintainers curating team knowledge and operators running the service are supporting users. Public reference collections can be shared. Workspace ownership applies to configured collection memberships, saved investigations/annotations when implemented, and later authorized team documents; it does not require a separate copy of every public page per tenant. Privileged administration and actual private workspace access remain authenticated/authorized. Public demo workspace switching is a demonstration interaction, not proof of private isolation.

The illustrative E104/release-2.4 upload question in the handoff describes the intended experience; it is not evidence of a real product, error, incident, or workaround. The public collection below uses credible public references. Synthetic team material is a separate optional guided collection and test fixture.

## First-visit journey and success criteria

Planned journey, not a UI implemented today:

1. **Purpose:** “Answers for Python file-processing tools, grounded in the documentation for your selected release.” Show collection scope, supported versions and provider/data disclosure.
2. **Try:** choose a version and one of the five useful questions, or type a question, without requiring an account to read the published public collection. Keep requests/output/context budgets, abuse controls and free-capacity limits explicit; no arbitrary uploads or source administration on this path.
3. **Inspect the answer:** display answered/partial/insufficient status, nearby trusted citations, platform/version qualifiers and missing/conflicting evidence.
4. **Inspect the evidence:** expand actual supplied passages with heading/location, source type, version/revision/hash and source link. Explain omitted passages and historical issue context; navigation or inaccessible sources do not silently broaden the query scope.
5. **Optionally explore:** an explicitly labeled synthetic guided scenario demonstrates team differences, outdated instructions or an evidence gap. Its selected collection/banner/source labels remain visible. Sign-in is needed for real private workspaces and privileged administration, not for the basic public value.

| Goal | Explicit delivery evidence to collect later |
| --- | --- |

Record a small actual walkthrough, task outcomes and feedback, including failure/confusion; disclose participant/sample scope and do not invent users or call assistant testing human validation |
| Semantic usefulness | Run the five source-verified public dev cases through the actual pipeline and review correctness, qualifications, source support, citation placement/coverage, partial answers, appropriate and false abstention separately. Useful follow-up questions outside the examples must also be reviewed; passing structure alone is insufficient |
| Inspectability | The visible passages/citations match the actual supplied evidence, selected release/collection and recorded revision; examples execute real retrieval/generation and expose provider errors. Replays, if offered, are distinctly labeled |
| Engineering behavior | Actual endpoint/DB and later worker/retrieval tests establish the stated allow/deny, persistence, recovery and revision behavior. Public-only grants never expose private/scenario content by default; optional guided selection is not substituted for private authorization tests |
| Cost/data/operations | Public requests obey explicit bounded generation/quotas and fail readably when capacity is exhausted; no paid fallback. Only suitable public/synthetic inputs go to the configured provider. Later record workload, latency/resource/cost and recovery evidence before claiming operational readiness |

Visitor usefulness, semantic outcomes and public-delivery criteria remain unmeasured. Stage 1's local authentication/source-ownership checks verify only their stated subset of engineering behavior; they do not establish independent human review, broad accuracy, demand or production capacity. Define a modest workload and walkthrough protocol before setting numeric service/quality targets. A minimal visitor view is a later presentation unit after the answer API, planned with Stage 8 delivery; Stage 0/1 do not add a UI or frontend framework.

## Architecture and migration contracts

The expanded deployment grows toward an API, worker, PostgreSQL, Redis broker, and a local development identity provider. They are introduced when needed. [Architecture](architecture.md) shows the data paths. SQLAlchemy manages transactions; Celery executes work; neither decides who may access a source or which revision is safe to publish.

| Existing contract to preserve | Expanded boundary |
| --- | --- |
| Schema-1 Source requires HTML-origin metadata and HTTPS locations | New named service schema, e.g. `doclens-service-v1`, separate from baseline integer 1. Split SourceRegistration, immutable SourceRevision, normalized Document and SourceLocation; never reinterpret old schema 1 silently |
| Source/chunk IDs scoped by product/version/URL/content/policy | Workspace-scoped identities and uniqueness; record source revision separately so unchanged passage identity and new snapshot provenance are both representable. Specify exact fingerprint/migration tests before writing new IDs |
| Citation means HTTPS page plus fragment; Python URL prefix must match release | Trusted typed locations: official page/anchor, pinned repository file/lines, PDF page, ticket/comment. Local/raw artifacts resolve through an authorized API endpoint; no invented HTTPS links or exposed machine paths |
| Full SQLite replacement and frozen labels | Separate PostgreSQL database/migrations and expansion corpus/eval version; explicit imports keep original hashes/IDs as provenance. Baseline commands/index/reports stay available and unchanged |
| Stable whole code blocks and exact provenance | Thin validated adapter over library output. Carry product, applicable version, source/revision/hash, purpose, authority/status, visibility, headings, code and locations through chunks/evidence |
| One injectable completion and structural validation | New transport behind the Generator contract, mapped into existing statuses/errors. Keep free-price/capability checks, zero-price caps, disabled paid fallback, redaction, finish/model/usage/latency validation and current prompt budgets |

Use authenticated `(issuer, subject)` for identity, then current DB membership/role for a workspace request. The workspace in a path is a requested scope, not authorization. Initially owner/editor may register sources; viewer may list/read. Bootstrap memberships through a trusted development/admin path, not a caller-selected workspace or public self-assignment endpoint. Initial visibility is workspace membership; individual/group document grants need an explicit later policy before ingestion claims to preserve them. Reject or quarantine finer-grained upstream permissions until supported, rather than widening them to the whole workspace.

Later public reading is an explicit, separately tested policy, not removal of Stage 1 authentication. A curator-owned public collection can publish selected source revisions for read-only visitors; private workspace endpoints, configuration and saved investigations/annotations remain membership-scoped. Sharing does not grant public write access or expose all sources in the curator's workspace. The server resolves a visitor's requested collection/mode/version into currently permitted published revisions; the browser cannot turn an arbitrary workspace into a public collection. Default queries exclude guided/synthetic collections unless deliberately selected. Any future anonymous answer/evidence/citation route must enforce those read grants, provider budgets and abuse limits before public deployment. Exact publication schema and routes are designed/tested in the retrieval/answer stages, not added to Stage 1 now.

Every ingestion, source/job lookup, retrieval, raw-artifact read, and citation resolver must enforce scope. Filter authorized, enabled, published content and product/version before top-k; do not fetch all tenants and discard forbidden results afterward. Recheck current authorization before evidence leaves the service for generation and before returning the response. Current membership/source access is checked independently of old embeddings; confirmed revocation must block subsequent access without waiting for reprocessing. Stage 6 adds lifecycle reconciliation, not the first authorization boundary. Do not log forbidden resource contents; future caches/traces must preserve access boundaries too.

Stage 2 persists a job and dispatch intent in one DB transaction, publishes that intent through Celery, and reconciles missed dispatch/duplicate execution. Task messages identify work; PostgreSQL is the source of job/revision truth. Save immutable, hash-verifiable raw artifacts and staged parsed records before a transactional ready/publication step. Bound network/parser attempts; preserve the last usable published revision after content-processing failure. Failed acquisition/listing never proves deletion. Stage 6 adds incremental reuse keyed by content **and** parser/chunker/embedding configuration, stale retirement, confirmed deletion, and access reconciliation. Revision publication cannot temporarily expose a mixture of old/new chunks.

Use a direct application pipeline for expanded RAG. CPU-heavy parsing/embedding belongs in workers; `async def` alone does not move blocking/CPU work away from an API event loop. Start service DB routes with straightforward synchronous SQLAlchemy/psycopg lifetimes; evaluate asynchronous clients at an actual I/O boundary when needed. Keep clients/credentials outside serializable domain records, close sessions/clients with context managers, and make failures observable without raw secret-bearing payloads.
